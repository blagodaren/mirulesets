MIRulesets объединяет источники и собственные правила, проверяет результат и публикует готовые файлы по постоянным ссылкам. Один бинарный файл содержит сервер, веб-панель и CLI-конвертер; Node.js, Python и установленное ядро прокси для работы не нужны.

> [!NOTE]
> **0.1.0-alpha — предварительная версия.** [Состав выпуска и ограничения](docs/releases/0.1.0-alpha.md). Для резервной копии сохраняйте весь каталог данных: экспорт из панели переносит настройки без секретов и истории сборок.

## Локальный запуск

### Готовый бинарник

Скачайте архив своей платформы из [релиза 0.1.0-alpha](https://github.com/blagodaren/mirulesets/releases/tag/v0.1.0-alpha), распакуйте и запустите приложение из этого каталога:

| Система | Команда | Прочитать пароль в другом терминале |
| --- | --- | --- |
| Windows, PowerShell | `.\mirulesets.exe` | `Get-Content data/admin-password` |
| Linux / macOS | `./mirulesets` | `cat data/admin-password` |

Откройте [http://127.0.0.1:8080](http://127.0.0.1:8080) и войдите с полученным паролем. По умолчанию файлы хранятся в `data` рядом с текущим рабочим каталогом. Другой путь задаётся через `MI_DATA_DIR`, собственный пароль — через `MI_ADMIN_PASSWORD` или `MI_ADMIN_PASSWORD_FILE`. Сервер автоматически не читает `.env`: этот файл использует Docker Compose.

### Из исходников

Требуется Go 1.26+. При первом запуске приложение создаст случайный пароль в `data/admin-password`; каталог данных не входит в Git.

1. Запустите `go run ./cmd/mirulesets` из каталога проекта.
2. Прочитайте пароль: PowerShell — `Get-Content data/admin-password`; Linux/macOS — `cat data/admin-password`.
3. Откройте [панель](http://127.0.0.1:8080) и войдите.
4. Сохраните новый набор: нажмите «Создать набор», укажите название, имя в ссылке, behavior, источники и свои правила, затем «Сохранить набор». Группа Mihomo по умолчанию — `PROXY`.
5. Откройте карточку сохранённого набора и нажмите «Собрать».

После успешной сборки в карточке доступны файлы и конфигурация Mihomo. Для ручного запуска отключите «Обновлять автоматически» перед сохранением; при включённом режиме планировщик запустит первую сборку сам. Интервал проверки — 15 секунд.

Оформление переключается в верхней панели и на экране входа: светлое, тёмное или системное. По умолчанию панель следует теме ОС; выбранный режим сохраняется в этом браузере.

Для VPS перейдите к [развёртыванию](#развёртывание): Docker, HTTPS, nginx, Nginx Proxy Manager, Caddy и systemd.

Если локальный Mihomo TUN возвращает fake-IP `198.18.x.x` для публичных доменов, перед запуском задайте в PowerShell `$env:MI_SOURCE_ALLOWED_CIDRS='198.18.0.0/15'`. Без этого явного исключения защита загрузчика отклонит служебный DNS-адрес. На VPS с обычным DNS настройка не требуется.

## Возможности

| Раздел | Что можно сделать |
| --- | --- |
| **Источники** | Объединить HTTP(S), S3 и другие наборы; задать приватные заголовки, фильтры, свои правила и исключения; развернуть ASN в CIDR |
| **Форматы** | Читать YAML, text, MRS, geosite/geoip DAT, hosts, DNS-подмножество Adblock и sing-box JSON; публиковать YAML, text, MRS, sing-box JSON и SRS |
| **Надёжность** | Остановить сборку при резком падении числа правил, увидеть diff и статусы источников, откатиться с удержанием выбранного поколения |
| **Клиенты** | Получить постоянные ссылки и общий YAML для Mihomo, проверить попадание домена/IP в наборы, посмотреть число скачиваний |
| **Управление** | Обновлять по расписанию, повторять неудачные отправки S3, клонировать и искать наборы по тегам, переносить настройки и применять YAML при старте |

Локальные файлы публикуются атомарно. На сборку работают четыре загрузчика; одновременно выполняются две сборки. Для HTTP используются ETag и Last-Modified. HTTPS доступен через встроенный ACME, внешний прокси или свои PEM-сертификаты.

## Развёртывание

[Docker](#docker-и-прокси-на-vps) · [Автоматический HTTPS](#автоматический-сертификат-без-nginx) · [nginx](#внешний-nginx) / [NPM](#nginx-proxy-manager-или-caddy-в-docker) · [Caddy](#caddy-на-vps) · [S3](#s3-minio-и-cloudflare-r2)

Выберите один способ TLS: встроенный ACME, внешний прокси или собственный сертификат. Для одного экземпляра приложения достаточно Docker Compose и постоянного тома `/data`.

### Docker и прокси на VPS

Готовый образ: `ghcr.io/blagodaren/mirulesets:0.1.0-alpha` для Linux amd64 и arm64. Он скачивается без входа в реестр. После настройки `.env` по шагам ниже можно запустить образ без локальной сборки:

```sh
docker run -d --name mirulesets --restart unless-stopped \
  --env-file .env -p 127.0.0.1:8080:8080 \
  -v mirulesets-data:/data \
  ghcr.io/blagodaren/mirulesets:0.1.0-alpha
```

Следующие команды Docker Compose предназначены для сборки из исходников.

Выполняйте команды из корня этого репозитория. Нужны Docker Engine и Docker Compose. Для дополнительных compose-файлов требуется Compose 2.24.4 или новее: `!override` заменяет список портов, чтобы HTTP-порт не остался опубликован по ошибке. [Правила объединения Compose](https://docs.docker.com/reference/compose-file/merge/)

1. Создайте файл настроек:

   ```sh
   cp .env.example .env
   chmod 600 .env
   ```

2. Получите пароль:

   ```sh
   openssl rand -hex 24
   ```

3. Запишите результат в `MI_ADMIN_PASSWORD` внутри `.env`. Минимум — 12 символов. Для доступа через домен задайте `MI_PUBLIC_URL=https://rules.example.com`.

4. Соберите и запустите приложение:

   ```sh
   docker compose up -d --build
   ```

5. Откройте `http://localhost:8080` на самой машине. Для удалённой VPS используйте SSH-туннель:

   ```sh
   ssh -L 8080:127.0.0.1:8080 user@your-vps
   ```

Приложение работает от UID/GID `10001:10001`; корневая файловая система контейнера доступна только для чтения. Именованный том создаётся с нужным владельцем. При замене на bind mount заранее создайте каталог данных с владельцем `10001:10001`.

### Автоматический сертификат без nginx

<details>
  <summary>Встроенный ACME: DNS, порты и запуск</summary>

В этом режиме MIRulesets обслуживает HTTPS самостоятельно. HTTP используется для ACME-проверки домена и перенаправления на HTTPS; сертификат и ключ сохраняются в томе данных. Домен должен указывать на VPS, входящие TCP 80 и 443 должны быть доступны. Если есть AAAA-запись, IPv6 тоже должен вести на эту VPS.

1. Добавьте в `.env`:

   ```dotenv
   MI_DOMAIN=rules.example.com
   MI_ACME_EMAIL=admin@example.com
   ```

2. Проверьте DNS и освободите порты 80/443 от другого веб-сервера.

3. Запустите конфигурацию ACME:

   ```sh
   docker compose -f compose.yml -f compose.acme.yml up -d --build
   ```

4. Откройте `https://rules.example.com`. Получение первого сертификата может занять несколько секунд. Смотрите результат в журнале:

   ```sh
   docker compose -f compose.yml -f compose.acme.yml logs --tail=100 mirulesets
   ```

`MI_PUBLIC_URL` в этом режиме устанавливается из `MI_DOMAIN`. Контейнер слушает непривилегированные порты 8080/8443; Docker перенаправляет к ним 80/443. Сохраняйте тот же набор `-f` для последующих команд управления контейнером. Wildcard-сертификаты и DNS-01 через API DNS-провайдера этой конфигурацией не предоставляются.

</details>

### Внешний nginx

<details>
  <summary>Конфигурация nginx и доверенные прокси</summary>

Используйте обычный `compose.yml`, а не `compose.acme.yml`. В `.env` задайте публичный HTTPS-адрес. TLS завершает nginx, приложение слушает HTTP только на loopback.

1. Откройте `deploy/nginx.conf`.
2. Замените `rules.example.com` и пути к уже полученным сертификатам.
3. Установите конфигурацию в nginx на VPS.
4. Проверьте её командой `sudo nginx -t`.
5. Примените командой `sudo systemctl reload nginx`.

Пример передаёт `Host` и `X-Forwarded-Proto`, допускает загрузки до 40 MiB и даёт сборке до 300 секунд. Проверка и обновление сертификата принадлежат вашему nginx/ACME-клиенту. [Документация nginx proxy](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)

Для корректного ограничения попыток входа настройте `MI_TRUSTED_PROXIES`: приложение принимает `X-Forwarded-For` только от явно доверенного прямого подключения. Для **нативного бинарника** и nginx на той же машине подходит `MI_TRUSTED_PROXIES=127.0.0.1/32,::1/128`. При nginx на хосте и приложении в Docker адресом подключения обычно будет gateway Docker-сети; укажите его точный адрес с `/32`, проверив сеть контейнера через `docker inspect`. Без этого параметра все пользователи за одним прокси делят общий лимит попыток входа.

</details>

### Caddy на VPS

<details>
  <summary>Caddy как внешний прокси</summary>

1. Задайте `MI_PUBLIC_URL=https://rules.example.com` в `.env`.
2. Запустите обычный `docker compose up -d --build`.
3. Замените домен и email в `deploy/Caddyfile`.
4. Установите этот файл как конфигурацию Caddy.
5. Проверьте и примените её штатными командами своей установки Caddy.

Caddy получает и обновляет сертификаты для публичного домена автоматически. Ему нужны корректные DNS-записи, доступные 80/443 и постоянный каталог данных. [Automatic HTTPS](https://caddyserver.com/docs/automatic-https)

</details>

### Nginx Proxy Manager или Caddy в Docker

<details>
  <summary>Общая Docker-сеть и TLS на прокси</summary>

`127.0.0.1` внутри контейнера прокси указывает на сам прокси. Для связи с приложением используйте общую Docker-сеть.

1. Создайте сеть, если её ещё нет:

   ```sh
   docker network inspect proxy >/dev/null 2>&1 || docker network create proxy
   ```

2. Подключите существующий контейнер прокси к сети `proxy` через его Compose-конфигурацию.
3. Задайте `MI_PUBLIC_URL=https://rules.example.com` в `.env`.
4. Запустите приложение в общей сети:

   ```sh
   docker compose -f compose.yml -f compose.proxy.yml up -d --build
   ```

5. Создайте Proxy Host в Nginx Proxy Manager: домен `rules.example.com`, scheme `http`, forward hostname `mirulesets`, port `8080`. Во вкладке SSL запросите сертификат Let's Encrypt и включите Force SSL.

В Advanced NPM при больших загрузках укажите:

```nginx
client_max_body_size 40m;
proxy_read_timeout 300s;
proxy_send_timeout 300s;
```

Для контейнерного Caddy замените upstream в Caddyfile на `mirulesets:8080`. Не публикуйте порт приложения наружу: `compose.proxy.yml` снимает публикацию 8080. NPM поддерживает получение сертификатов и завершение TLS в интерфейсе. [Руководство NPM](https://nginxproxymanager.com/guide/)

Для IP-лимита входа задайте `MI_TRUSTED_PROXIES` равным отдельной доверенной подсети прокси. Посмотреть её можно командой:

```sh
docker network inspect proxy --format '{{range .IPAM.Config}}{{println .Subnet}}{{end}}'
```

Например, если сеть действительно имеет диапазон `172.30.90.0/24`, укажите `MI_TRUSTED_PROXIES=172.30.90.0/24`. Все контейнеры этой сети получают право передавать адрес клиента; подключайте к ней только доверенные сервисы. Более узкий вариант — статический адрес самого прокси с `/32`. Не используйте `0.0.0.0/0` или `::/0`. После изменения окружения пересоздайте контейнер.

</details>

### Собственные сертификаты

<details>
  <summary>HTTPS с готовыми PEM-файлами</summary>

При запуске бинарника установите:

```dotenv
MI_TLS_MODE=manual
MI_TLS_ADDR=:8443
MI_TLS_CERT=/etc/mirulesets/fullchain.pem
MI_TLS_KEY=/etc/mirulesets/privkey.pem
MI_PUBLIC_URL=https://rules.example.com
```

Предоставьте процессу чтение PEM-файлов. Для контейнера добавьте read-only mounts обоих файлов и публикацию `443:8443` в свой override. `compose.yml` принудительно задаёт `MI_TLS_MODE=off`, поэтому в override также задайте `MI_TLS_MODE: manual`. Обновление файлов сертификата выполняет ваш ACME-клиент; после замены перезапустите приложение.

</details>

### S3, MinIO и Cloudflare R2

<details>
  <summary>Подключение хранилища, публикация и повторы</summary>

Приложение пишет готовые файлы в настроенный bucket и может читать исходники по ссылкам `s3://bucket/path/file.mrs`. Bucket создаётся заранее. Доступ к S3 задаётся через окружение сервера; секретный ключ не передаётся браузеру. Используется S3 Signature V4 через MinIO Go SDK. [API SDK](https://docs.min.io/aistor/developers/sdk/go/api/)

Для AWS S3:

```dotenv
MI_S3_ENDPOINT=s3.eu-central-1.amazonaws.com
MI_S3_REGION=eu-central-1
MI_S3_BUCKET=my-rulesets
MI_S3_ACCESS_KEY=your-access-key
MI_S3_SECRET_KEY=your-secret-key
MI_S3_PREFIX=rules
MI_S3_SECURE=true
MI_S3_PATH_STYLE=false
MI_S3_PUBLIC_URL=https://cdn.example.com
```

Для MinIO замените endpoint, регион и способ адресации:

```dotenv
MI_S3_ENDPOINT=https://minio.example.com
MI_S3_REGION=us-east-1
MI_S3_PATH_STYLE=true
```

Для Cloudflare R2:

```dotenv
MI_S3_ENDPOINT=https://ACCOUNT_ID.r2.cloudflarestorage.com
MI_S3_REGION=auto
MI_S3_PATH_STYLE=true
```

R2 использует S3 API с регионом `auto`. Для публичной раздачи настройте домен bucket и укажите его как `MI_S3_PUBLIC_URL`. [Совместимость R2 с S3 API](https://developers.cloudflare.com/r2/api/s3/api/)

`MI_S3_PUBLIC_URL` — URL корня bucket; `MI_S3_PREFIX` добавляется приложением при публикации. Значение prefix по умолчанию — `rules`. Ключи стабильны: `<prefix>/<id>.{mrs,yaml,txt,json,srs}` в выбранных форматах; например, `https://cdn.example.com/rules/example.mrs`. Если SHA-256 файлов не изменились и предыдущая загрузка в тот же S3 завершена, повторной отправки нет. После ошибки или смены назначения S3 публикация повторяется. Входной `s3://bucket/import/source.mrs` читается по точному ключу `import/source.mrs`, без добавления prefix. Разрешён только настроенный bucket. Размер одного входного S3-объекта ограничен 32 MiB.

Локальная публикация переключается на завершённое поколение файлов атомарно. В S3 обновление нескольких объектов одной транзакцией недоступно: потребители могут короткое время видеть разные поколения форматов. При частичном сбое S3 локальная сборка всё равно публикуется, а поле `LastError` у набора перечисляет форматы, которые не удалось загрузить. Для включённого набора планировщик повторяет попытку через 1, 5, 15, затем 60 минут; успешная публикация сбрасывает задержку. Ручная сборка доступна сразу.

Для приватного bucket оставьте `MI_S3_PUBLIC_URL` пустым. Приложение не меняет bucket policy и не делает объекты публичными. Автоматическая генерация presigned-ссылок не выполняется. Доступ на запись должен разрешать `PutObject` для выбранного префикса, чтение источников — `GetObject`; проверка bucket через HEAD может требовать отдельного разрешения на bucket. При запуске сервер проверяет bucket с тайм-аутом 15 секунд; при недоступности записывает предупреждение и продолжает локальную раздачу. Эта проверка не подтверждает права на запись. `MI_S3_SESSION_TOKEN` поддерживает временные S3-учётные данные, обновляемые оператором.

После изменения `.env` пересоздайте контейнер командой своего режима `docker compose ... up -d`; обычный `restart` не обновляет окружение.

Удаление набора прекращает локальную раздачу: ссылки `/rules/<id>.<format>` возвращают 404, каталог локальных артефактов удаляется. Очистка поколений выполняется после успешной публикации и при запуске: остаются текущее и одно предыдущее. Незавершённые поколения удаляются после ошибки; оставшиеся после аварии каталоги удалённых наборов очищаются при следующем запуске. Ошибки очистки записываются в журнал.

</details>

### Бинарник и systemd

<details>
  <summary>Установка сервиса и параметры окружения</summary>

Для сборки нужен Go 1.26 или новее. Бинарник содержит веб-интерфейс, Node.js для запуска не требуется.

1. Соберите на Linux:

   ```sh
   CGO_ENABLED=0 go build -trimpath -ldflags='-s -w' -o mirulesets ./cmd/mirulesets
   ```

2. Установите бинарник и системного пользователя:

   ```sh
   sudo install -m 0755 mirulesets /usr/local/bin/mirulesets
   id mirulesets >/dev/null 2>&1 || sudo useradd --system --no-create-home --shell /usr/sbin/nologin mirulesets
   ```

3. Создайте `/etc/mirulesets.env` с паролем и публичным URL. Ограничьте права: `sudo chmod 600 /etc/mirulesets.env`.
4. Установите unit:

   ```sh
   sudo install -m 0644 deploy/mirulesets.service /etc/systemd/system/mirulesets.service
   sudo systemctl daemon-reload
   ```

5. Запустите сервис:

   ```sh
   sudo systemctl enable --now mirulesets
   ```

Unit рассчитан на внешний reverse proxy и хранит данные в `/var/lib/mirulesets`. Для автоматического TLS непосредственно в systemd потребуются адреса `:80`/`:443` и явное разрешение `CAP_NET_BIND_SERVICE` в вашем override; контейнерный вариант ACME обходится без этой привилегии.

Дополнительные параметры окружения для бинарника:

| Переменная | Назначение |
| --- | --- |
| `MI_ADMIN_PASSWORD_FILE` | Прочитать пароль из файла, доступного процессу. Имеет приоритет над `MI_ADMIN_PASSWORD`; в контейнере файл надо примонтировать отдельно. |
| `MI_API_TOKEN` | Необязательный API-токен от 32 символов для `Authorization: Bearer …`. |
| `MI_METRICS_TOKEN` | Необязательный токен только для `/metrics`: от 32 символов, без переводов строк, должен отличаться от `MI_API_TOKEN`. |
| `MI_TRUSTED_PROXIES` | CIDR доверенных прямых прокси через запятую. Только их `X-Forwarded-For` учитывается для лимита входа. При прямом доступе оставьте пустым. |
| `MI_ALLOW_PRIVATE_SOURCES=true` | Разрешить HTTP-источники из локальных/служебных сетей. По умолчанию такие адреса и перенаправления к ним запрещены. |
| `MI_SOURCE_ALLOWED_CIDRS` | Точечные исключения из запрета служебных адресов, CIDR через запятую. Например, `198.18.0.0/15` для доверенного Mihomo TUN с fake-IP DNS. Остальные внутренние адреса остаются запрещены. |
| `MI_ACME_CA` | URL каталога ACME, например staging CA для проверки конфигурации без production-сертификата. |

Если при запуске бинарника не задан ни пароль, ни файл пароля, приложение создаёт случайный пароль в `<MI_DATA_DIR>/admin-password` с правами `0600`. В Compose пароль обязателен в `.env`. Пароль должен занимать от 12 до 72 байт; для сгенерированных ASCII-паролей это совпадает с числом символов.

</details>

### Данные, обновления и проверка

Сохраняйте весь каталог данных: конфигурацию, результаты сборок и кеш сертификатов. Для согласованной резервной копии остановите приложение на время копирования. Не запускайте несколько экземпляров с одним каталогом данных.

Для обновления исходников пересоберите контейнер командой `docker compose ... up -d --build`. Данные остаются в томе. Ошибки смотрите через `docker compose ... logs --tail=100 mirulesets`; для systemd — `journalctl -u mirulesets -n 100 --no-pager`.

Встроенный TLS на реальном домене требует проверки на вашей VPS. Локальные тесты не подтверждают доступность DNS, внешних портов, выдачу сертификата или права конкретного S3-аккаунта.

## Совместимость форматов

| Behavior | YAML | text (`.txt`, `.list`, `.lst`) | MRS | sing-box JSON / SRS |
| --- | --- | --- | --- | --- |
| `domain` | импорт / экспорт | импорт / экспорт | импорт / экспорт | JSON: импорт / экспорт; SRS: экспорт |
| `ipcidr` | импорт / экспорт | импорт / экспорт | импорт / экспорт | JSON: импорт / экспорт; SRS: экспорт |
| `classical` | импорт / экспорт | импорт / экспорт | не поддерживается самим Mihomo | только эквивалентные условия |

Дополнительные входные форматы: geosite/geoip DAT с выбором категории, hosts, DNS-подмножество Adblock и ASN → CIDR. URL-фильтры, косметика и исключения Adblock отклоняются. [Поддержанные конструкции и ограничения](internal/rules/README.md).

Справочник форматов Mihomo — [официальная документация rule-providers](https://wiki.metacubex.one/en/config/rule-providers/).

`auto` определяет **формат**, behavior задаётся явно. YAML должен содержать массив строк `payload` или `rules`; экспорт всегда использует `payload`. Это содержимое rule-provider, а не импорт полной конфигурации прокси. YAML-алиасы и несколько YAML-документов отклоняются.

Для `domain` строка `example.com` означает точное имя; `+.example.com` — имя вместе с поддоменами. Для `ipcidr` принимаются IPv4/IPv6 CIDR, а одиночные IP становятся `/32` или `/128`. Для `classical` указываются правила **без политики маршрутизации**: `DOMAIN-SUFFIX,example.com`, `IP-CIDR,203.0.113.0/24,no-resolve` и логические выражения Mihomo.

Источник может иметь другой behavior: domain/ipcidr преобразуются в classical. Обратное преобразование допускается только без потери смысла. Например, `DOMAIN-SUFFIX,example.com` → `+.example.com`; смешанный classical-набор или `no-resolve` при переводе в ipcidr вызывают ошибку. Неподдержанные строки не выбрасываются.

Исключения удаляют **точные нормализованные строки** после объединения источников и своих правил. Исключение `ads.example.com` не вычитает поддомен из `+.example.com`, а CIDR-исключение не вычитает подсеть из более широкого CIDR.

## Публикация и сохранность

Порог падения применяется только при неизменной ревизии конфигурации; после редактирования следующая сборка допускает сокращение правил, а diff рассчитывается всегда.

Файлы доступны по постоянным ссылкам `/rules/<id>.yaml`, `/rules/<id>.txt`, `/rules/<id>.mrs`, `/rules/<id>.json` и `/rules/<id>.srs` в выбранных форматах. Также принимаются `.yml` и `.list`. Панель/API защищены паролем; **ссылки на файлы открыты для клиентов**. Используйте внешний контроль доступа, если правила должны быть приватными.

При ошибке источника или конвертации предыдущая локальная сборка продолжает работать. Сначала создаётся полное поколение файлов, затем атомарно обновляется ссылка в `state.json`. При изменении настроек устаревшая сборка отмечается, а новый snippet доступен после успешной пересборки. Правки во время сборки отклоняются; ревизии предотвращают перезапись изменений из другой вкладки.

При включённом S3 файлы дополнительно загружаются в `<prefix>/<id>.<format>`. Чтение `s3://bucket/key` использует настроенный bucket и точный ключ. Публичный S3/CDN-адрес задаётся явно; приложение не изменяет ACL и политики bucket. Обновление нескольких S3-объектов не атомарно: при частичной ошибке локальная сборка готова, а панель показывает, какие форматы нужно отправить повторно.

Конфигурация хранится в `data/state.json`, файлы — в `data/artifacts`, ACME-кэш — в `data/certificates`. Используйте один процесс на каталог данных и делайте резервную копию каталога. HTTP-кэш находится в памяти. События сохраняются в `data/events.jsonl` с одним архивом, всего до 2 MiB; после перезапуска доступны последние 100 сохранившихся записей. В панели показываются последние пять, полный доступный список возвращает `/api/overview`.

Повторная проверка неизменённых правил обновляет время и метаданные сборки без нового поколения файлов. Сравниваются SHA-256 всех форматов; отсутствие или повреждение локального файла вызывает пересоздание поколения. Ошибки источника, кодирования и S3 включают задержки повторов 1 → 5 → 15 → 60 минут. Успех и сохранение настроек набора сбрасывают задержку; после перезапуска счётчик задержек начинается заново.

Для оповещений задайте `MI_ALERT_WEBHOOK_URL` и при необходимости `MI_ALERT_WEBHOOK_TOKEN`: [настройка журнала и webhook](docs/observability.md). Метрики доступны на защищённом `/metrics`: [конфигурация Prometheus с отдельным токеном](docs/observability.md#метрики-prometheus). CLI и API используют единую [версию сборки через `-ldflags`](docs/deployment.md#версия-сборки).

## Предпросмотр источника

1. Откройте редактор набора и нажмите «По ссылке» в разделе источников.
2. Укажите URL, формат и behavior источника.
3. Нажмите «Предпросмотр» в карточке источника.

Панель покажет число правил, размер загруженного файла, фактический формат и первые 200 правил. Изменения в полях используются сразу: сохранять или собирать набор не требуется. Повторный запрос заменяет предыдущий результат, ошибки загрузки и разбора отображаются под источником. Результат не сохраняется и не попадает в журнал событий.

Предпросмотр поддерживает `auto`, `yaml`, `text`, `mrs` и behavior `domain`, `ipcidr`, `classical`. Он использует тот же загрузчик и разбор, что сборка: лимит файла 32 MiB, запрет приватных адресов по умолчанию и чтение `s3://` только из настроенного bucket. Таймаут запроса — 60 секунд; одновременно выполняются не более двух предпросмотров, остальные запросы получают HTTP 429.

Для предпросмотра подходят только HTTP(S)/S3 URL. Внутренние ссылки `ruleset://`, ASN и остальные явно выбранные форматы проверяются при сборке. Предпросмотр использует только URL, формат и behavior: фильтры, категории DAT и HTTP-заголовки из карточки не применяются. Источник с обязательной HTTP-авторизацией нужно проверять сборкой набора.

`POST /api/preview` требует сессию панели или Bearer-токен и проверяет same-origin для сессии. Тело запроса: `{"url":"https://example.com/rules.mrs","format":"auto","behavior":"domain"}`. Ответ содержит `ruleCount`, `sizeBytes`, `format`, `behavior`, `lines` и `truncated`.

## CLI-конвертер

```sh
go build -o mirulesets ./cmd/mirulesets
./mirulesets convert -input domains.yaml -output domains.mrs -behavior domain -from yaml -to mrs
./mirulesets convert -input domains.mrs -output domains.txt -behavior domain -from mrs -to text
./mirulesets convert -input domains.txt -output classical.yaml -behavior domain -target-behavior classical -to yaml
```

В Windows используйте `mirulesets.exe`. Существующий выходной файл не перезаписывается: выберите новое имя.

## Проверки и ограничения

```sh
go test ./...
go vet ./...
go test ./internal/rules -run '^$' -bench BenchmarkDomainMRS100K -benchtime=3x -benchmem
```

Проверены сохранение/повторное открытие состояния, отсутствие публикации при сбое источника, auth/CSRF, HTTP-кэш, ограничения адресов источников, S3 SigV4 через тестовый сервер, конвертация и совместимость с официальным **Mihomo v1.19.34** в обе стороны. Реальные Google geosite и Telegram geoip MRS также проходят проверку. [Подробности кодека, fuzz-тесты и результаты замеров](internal/rules/README.md).

Локальный замер 100 000 доменов → MRS: **70,3 мс** на Ryzen 7 9800X3D, Go 1.26.3, Windows; это микробенчмарк, не гарантия времени сетевой сборки. Все сетевые операции выполняются отдельно от конвертера. Лимиты: загрузка источника для сборки или предпросмотра 32 MiB; распакованные/объединённые правила 64 MiB и до 1 000 000 строк; 256 источников в наборе, 1024 набора. Размер JSON-запроса редактирования — 4 MiB.

Приватные/служебные адреса HTTP-источников по умолчанию запрещены, включая перенаправления и DNS-подмену на этапе соединения. Для доверенной внутренней сети есть явная настройка `MI_ALLOW_PRIVATE_SOURCES=true`. Учётные данные S3 и пароль задаются на сервере и не возвращаются в API. Работа с реальным S3, выпуск сертификата и запуск Docker-контейнера требуют соответствующей инфраструктуры; локально контейнер не запускался, поскольку Docker daemon недоступен. Race detector на этом Windows-хосте недоступен без CGo/C-компилятора; в CI предусмотрен Linux-запуск с `-race`.
